## 👨‍💻 Code Style & Standards

To maintain a high-quality unified codebase, all Python code must adhere to the following standards. The project is configured with `pyproject.toml` to enforce these rules via **Ruff**.

### 1. Style Guide
*   **Formatter**: Use **Ruff** for strict formatting (black-compatible).
*   **Indent**: 4 spaces.
*   **Quotes**: Double quotes (`"`) for strings.
*   **Line Length**: 88 characters.

### 2. Imports
*   **Sorting**: Imports must be sorted and grouped in the following order:
    1.  Standard Library (e.g., `sys`, `pathlib`)
    2.  Third-Party Libraries (e.g., `yaml`, `jinja2`)
    3.  Local Application Imports (e.g., `packages.shared`, `packages.generator_nestjs`)
*   **Absolute Imports**: Prefer absolute imports for project modules over relative ones where possible, though relative imports are used in `__init__.py` or internal module references.
*   **Unused Imports**: Remove all unused imports.

### 3. Type Hinting
*   **Strict Typing**: All function signatures (arguments and return types) must be type-hinted.
*   **Generic Types**: Use `List`, `Dict`, `Optional`, `Any` from `typing` module for complex types.

### 4. Documentation
*   **Docstrings**: All public modules, classes, and functions must have docstrings.
*   **Format**: Use **Google-style** docstrings.
    ```python
    def my_function(param1: int, param2: str) -> bool:
        """Description of what the function does.

        Args:
            param1 (int): The first parameter.
            param2 (str): The second parameter.

        Returns:
            bool: The return value description.
        """
    ```

### 5. Linting & Validation
Run the standard linter before committing:
```bash
ruff check .
ruff format .
```

## 🎯 Project Overview

This is an **AI-powered NestJS application generator** that transforms natural language descriptions into NestJS backend code. The project supports three generation pipelines used in thesis experiments:

- **DSL**: natural language -> YAML blueprint -> deterministic Jinja2 rendering
- **Raw**: natural language -> JSON file map generated directly by the LLM
- **Mixed**: natural language -> YAML blueprint -> JSON file map generated by the LLM using the blueprint as context
- **Textual DSL**: natural language -> textual DSL source -> deterministic compiler -> YAML blueprint -> Jinja2 rendering

### Core Value Proposition
- **Natural Language to Code**: Describe your application in plain English, get production-ready NestJS code
- **Template-Driven**: Jinja2-based templates ensure consistent, maintainable code patterns
- **Full-Stack Generation**: Creates controllers, services, entities, DTOs, and modules
- **Database Integration**: Automatic TypeORM entity generation with relations

## 🔄 Workflow Process

### 1. Natural Language Processing (LLM Phase)
- **Input**: Plain English description of desired application
- **Process**: Selected LLM provider (Groq/Gemini/OpenRouter/Ollama) converts description to structured YAML
- **Output**: Raw LLM response with potential formatting issues

### 2. State Machine Repair (Sanitization Phase)
- **Input**: Raw LLM response (may contain markdown blocks, malformed JSON/YAML)
- **Process**:
  - `clean_llm_response()`: Removes markdown code blocks and provider-specific thinking wrappers
  - `try_parse_json()`: Fixes common LLM errors:
    - Unescaped newlines and quotes in strings
    - Missing closing braces
    - Control character escaping
    - Truncated JSON payload repair
- **Output**: Clean, valid YAML blueprint

### 3. Blueprint Validation (AI Phase)
```python
result = natural_language_to_yaml(description)
clean_yaml = result.content
```

### 4. Graph-based Relation Inference (DSL Phase)
- **Input**: YAML blueprint with entity relations
- **Process**: `handle_relations()` function:
  1. Creates relation graph: `{(Entity1, Entity2): relation_data}`
  2. Validates all referenced entities exist
  3. Detects bidirectional relations by checking reverse edges
  4. Automatically infers `inverseField` for bidirectional relations
- **Output**: Validated relations map with inverse field mappings

### 5. Code Generation (Template Rendering Phase)
- **Input**: Validated YAML blueprint with complete relation data
- **Process**: Jinja2 templates render TypeScript/NestJS code
- **Output**: Complete NestJS application structure

## 📝 Blueprint Schema

The YAML blueprint follows this structure:

```yaml
root:
  name: AppName
  database:
    type: sqlite
    database: ./data/app.db
    synchronize: true
    logging: false
  features:
    cors: true
    swagger: true

modules:
  - name: User
    generate: [controller, service, module, entity, dto]
    entity:
      fields:
        - name: email
          type: string
          required: true
          validation: {isEmail: true}
      relations:
        - type: OneToMany
          model: Post
          field: posts
```

## 🤖 AI Integration Details

### LLM Configuration
- **Architecture**: Single selected provider per run
- **Supported Providers**: Groq, Gemini, OpenRouter, Ollama
- **Temperature**: 0.1 (low for consistent output)
- **Framework**: LangChain with provider-specific implementations
- **Environment Variables**:
  - `GROQ_API_KEY` (recommended)
  - `OPENROUTER_API_KEY` (optional)
  - `GOOGLE_API_KEY` (optional)
  - Ollama local installation (optional)

### Prompt Engineering
The system uses prompt templates in `packages/llm_providers/core/prompts.py` that:
- Enforce strict YAML output for the DSL pipeline
- Enforce strict JSON file-map output for raw and mixed pipelines
- Include entity relationship modeling guidance
- Require raw/mixed outputs to include runnable NestJS bootstrap files

## 🛠️ Usage Instructions

### For AI Agents

1. **Generate from Natural Language**:
```bash
nestforge dsl "Create an e-commerce API with products, customers, and orders" --model gemini
nestforge raw "Create a blog API" --model gemini
nestforge mixed "Create a blog API" --model gemini
```

2. **Use Existing Blueprint**:
```bash
nestforge dsl "My app" --blueprint blueprint.yaml --project ./nest_project
```

3. **Run Experiment Batch**:
```bash
python -m apps.experiments.runner --approach all --provider openrouter
python -m apps.experiments.analysis --results results/test_results.json
python -m apps.experiments.export_analytics
```

Experiment code lives in `apps/experiments/`. Experiment inputs, outputs, archives, logs, and analytics live in `results/`.

4. **Run Generated Application**:
```bash
cd nest_project
npm install
npm run start:dev
```

### For Developers

1. **Modify Templates**: Edit files in `packages/generator_nestjs/templates/` to change generated code patterns
2. **Extend AI Prompts**: Update prompt templates in `packages/llm_providers/core/prompts.py`
3. **Add New Generators**: Create new template files and update generation logic

## ⚠️ Important Notes for Agents

1. **Environment Setup**: Requires API key for the provider you choose (`GROQ_API_KEY`, `OPENROUTER_API_KEY`, `GOOGLE_API_KEY`, or local Ollama)
2. **File Paths**: All code lives in `packages/` (library) and `apps/` (entry points). No `src/` directory.
3. **Import Style**: Use absolute imports: `from packages.shared.logger import logger`, `from apps.experiments.runner import ...`
4. **Generated Code**: The `nest_project/src/` directory is auto-generated - don't manually edit
5. **Experiment Results**: `results/test_results.json` is append/resume oriented, so clear or archive it before running a fresh benchmark campaign. Timestamped source-of-truth runs are stored in `results/runs/`.
6. **Lint**: Run `ruff check . && ruff format .` before committing.
7. **Tests**: Run `python -m pytest` (419 tests, all pass).
